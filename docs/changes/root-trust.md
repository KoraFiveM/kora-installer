### Security
- **Root no longer trusts files in a server folder.** The server folder belongs to the server's own account (which runs third-party resource code) or to you, so Kora now checks everything it reads there before acting as root or administrator:
  - The automatic-update job (root on Linux, SYSTEM on Windows) only runs a kora program nobody else can change: Kora's own root-owned copy in `/opt/kora` (Windows: `%ProgramFiles%\Kora\bin`), or `kora` itself when it is installed in such a place, never a program named in the server's records. The Windows task definition is written to `%ProgramFiles%\Kora\tasks` instead of the server folder.
  - `kora delete` and `kora uninstall` only delete files and folders inside the server folder and never follow a symbolic link; they only remove this server's own `kora-<name>` system account, only delete the program copy inside Kora's program folder, hand a kept folder back only to a plain `uid:gid`, and never close the SSH port. With ufw only rules carrying Kora's label are removed. `kora uninstall` takes each server's name and ports from your server list.
  - Kora's records, the schedule setting and `secrets.env` are written without ever following a planted symbolic link.
- **The helper is limited to what the panel needs.** Through the helper a server is only installed into a new or empty folder in your home folder or in `/home/kora`, never from another catalogue (`--catalog`), and Kora is only updated to a newer version. Git run as root no longer reads your git settings or runs git hooks; your GitHub sign-in still works for private forks. The panel guide now says plainly that installing the helper gives your account the same power as passwordless `sudo` for Kora's actions.
- **Windows: Kora's folders in `%ProgramData%` must belong to administrators.** A `Kora`, `mariadb` or `tmp` folder that someone else created first is refused (delete it and try again); otherwise its owner is set to Administrators.
