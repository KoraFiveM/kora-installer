# Changelog

All notable changes to Kora Installer. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/);
versions follow [SemVer](https://semver.org/).

## [Unreleased]

### Changed (one error convention, no visible change except the fixes below)
- Errors that can reach a person are `Problem` values from where they are raised to where they are shown. `api::Res<T>` is `Result<T, Problem>`; `InstallError` is gone (the installer returns `Problem`), `StepError::Failed` holds a `Problem`, job bodies fail with a `JobFailure` (a `Problem` plus the install extras), the panel's `ApiError` is made from a `Problem`, and the command line prints one in one place. The packed-string form of a `Problem` (`encode`/`decode`/`is_encoded`/`plain_text`/`message_of`, `From<Problem> for String`) is deleted, and a test keeps it from coming back. Job errors already stored by 0.7.0 in the packed form still read (one read-only compatibility function in the store layer); nothing is written that way any more. The JSON error shape and the generated TypeScript are unchanged.
- Low-level errors (files, JSON, internet, git) become a plain sentence with the technical text in "Show details"; `Problem::context`, `lead` and `and_say` add words without losing the code or the choices. New codes: `io`, `data`, `network`, `storage_full`, `git.failed`, `server.not_kora`, `needs_db_password` (the same text as before, now raised by the engine instead of recognised from its words), `tls.expiring` and `tls.missing` (as constants). A server folder without `kora-server.json` answers with `server.not_kora` instead of a guess from the file error.

### Fixed
- A guided error (with its fix buttons) was flattened into plain text or lost its marker when Kora added words in front of it or passed it through a `String`: starting/stopping a server, reading the server list or a server's record, the registry, remembered answers and paused installs (a busy or damaged data file lost its "Try again" and "Copy details"), the administrator-service choices on installing Git, a job error that had a code but no buttons, the catalogue and automatic-update jobs. They arrive whole now.
- An update that is refused because another update is running is recognised by its code, not by its wording.

### Added
- **Kora's administrator service**, one small service per machine (Windows `KoraService`, systemd `kora.service`) that does a fixed list of validated administrator operations for the unprivileged per-user panel. It is installed with the program, in a folder only administrators can change, by a new **Windows installer (`.msi`**: Program Files, the service, PATH, Start Menu and Desktop shortcuts, upgrade and uninstall in Apps & features) and a new **Linux `.deb`** (or `sudo kora service install` on other systemd distributions), with ONE administrator approval at install time. After that nothing asks again: the panel installs and removes servers' services, firewall rules and databases, changes update schedules and updates Kora with no prompt and no terminal, from this computer or from another device. `install.sh` and `install.ps1` offer the system install first (per-user stays available, `KORA_SYSTEM=0` / `-PerUser`).
- `kora service status|list|allow|deny|install|uninstall|migrate|finish-upgrade`: who may use the service (an explicit list, the installing account first), installing and removing it, and bringing an earlier layout over. Identity is read from the connection (Windows token SID and integrity, Linux `SO_PEERCRED`) on every request; every operation is checked on the privileged side (folder owner without following links, ports from the folder's record, the ownership ledger `owners.json`), runs the protected program with a clean environment, and is written to an audit log (no paths, no secrets).
- Updating Kora through the service, with rollback: the previous program is kept, the new one must start (else the old is put back at once), the service restarts on it, and rolls back by itself after three starts that do not stay up.
- When the service is not installed (a per-user install) the panel says so and offers **Install Kora's administrator service** (Windows: runs the checked installer with one prompt; Linux: shows `sudo kora service install`), **Continue without the administrator parts**, or **Show me the command**. `GET /system` has `admin_service` (`ready` / `missing` / `not_allowed`); `POST /system/admin-service/install` (local only); the wizard's last screen says what the service does or what is missing.
- Migration from 0.7.0 and 0.6.x (`kora service migrate`, run by the package and the MSI; per-user part in "Tidy up old shortcuts"): the old Linux helper is removed and its account stays allowed; update tasks that still run with full administrator rights are rewritten to unelevated; servers set up the old way (including root-run installs whose folders belong to the server's own account) are recorded as yours; your own earlier copy of Kora is set aside as `.previous` and the background panel points at the installed program. Servers and data are never touched.

### Added (merge of the store, reach, clone-or-fork and desktop work)
- The Kora desktop app is part of the Windows installer (an optional feature, `DESKTOP=0` leaves it out; the Start Menu and Desktop shortcuts start it) and of a new `kora-desktop` Linux package; the release builds it, signs it with the same signing step and includes it in the checksums and the attestation.
- "Install Kora's administrator service" inside the desktop app opens Windows' permission prompt in front of the app window.
- "Open the firewall for this server's game port" (Reachability) goes through the administrator service when Kora is not elevated (game port only, TCP and UDP, same port rules, recorded in the service's ownership records); without the service the answer offers the install or `kora reach <name> --open-firewall` for an administrator terminal.

### Changed
- Update schedules through the administrator service take the server's folder, never a name looked up in the person's own server list, and a child of the service never opens a person's data file (`store/kora.db`); the migration reads the list read-only (`store::peek`) and still accepts an old `servers.json`.
- **The Windows UAC worker and the optional Linux helper are gone** (`kora helper`, `kora admin-worker`, the permission prompt, the `X-Kora-Admin` header, the `admin.*` problem codes and the `request_admin` fix action). They elevated a program in a user-writable folder and could not work with nobody at the desktop. `request_admin` became `install_admin_service`; new problem codes `service.not_allowed` and `service.lost`.
- The Linux service step hands the server folder to its own account through open folder handles (`fchownat`, never through a link) instead of `chown -R <path>`; deleting a server through the service hands it back to the account that asked, so the panel can delete the files as that person.
- The unattended-update task made through the service always runs as you, unelevated; "run as the system account" stays a command for an administrator terminal.
- `kora uninstall` (everything Kora set up) and removing the old machine-wide app are commands for an administrator terminal; the service never does them.
- **Backups of a server, and restoring them.** A new **Backups** tab on every server and `kora backup create|list|verify|restore|undo|delete|prune|schedule <server>`. One backup is one archive file (`<name>-<date>.tar.gz`, or `.tar.gz.age` when password protected) with a small listing file next to it: the server's own database as a consistent logical dump (`mariadb-dump` / `mysqldump` with `--single-transaction --routines --triggers --events`, only that database, with the server's own login from `database.json`, the password in the environment and never on a command line), `server.cfg`, `permissions.cfg`, `secrets.cfg`, `database.json`, txAdmin's data, Kora's records for the server, and the resources: **by reference** (repository, branch and exact commit; the archive stays small) where they can be fetched again, and **in full, with their git history** where they cannot (changes made here, kept-aside changes, commits that exist only here, paid assets, folders that are not git copies), or everything in full on request. The FXServer build is not in it (it is downloaded again; its number is recorded). It can be made while the server runs (the database is one snapshot, the files are copied one by one and a file seen changing is noted) or with **Stop the server during the backup** for a strictly consistent copy. The file holds secrets and says so: it is made owner-only from the first byte (0600; the Windows access list for the default folder and `icacls` for a chosen one), and only administrators can download it. **Password protection** uses the `age` format (passphrase mode: scrypt + ChaCha20-Poly1305, through the `age` crate, so `age -d` opens a Kora backup): off by default for backups kept on this computer's own disk (the same secrets already sit in plain text next to it, and a lost password makes a backup useless), required for a file made to move a server; a lost password cannot be recovered and the screens say so. Backups go to Kora's own folder in the Kora home, outside every server folder (deleting a server does not delete its backups), or a folder you choose (another disk, a mounted share), with a free-space check first and retention (keep the newest N, and/or one per day for D days; a safety copy is kept 30 days and a copy made for moving is never pruned). Where backups go is a small `Destination` trait so a remote destination can be added later. A backup that fails (disk full, the database not running with a **Start it for me** button, the dump tool missing with the install fix, a destination that cannot be written, a wrong password) says what to do. Operators may make and check a backup and preview a restore; restoring, undoing, deleting, pruning, changing the settings and downloading are administrators', and held back from a remote sign-in made with a token until `kora panel remote-actions on`.
- **Restore** onto the same server: pick a backup, read what will change and what stays, Kora checks every file against its checksums before touching anything, makes a **safety copy** of the server as it is now, stops the server, puts the database back (before any file, so a database failure leaves the files alone), the files (`secrets.cfg` and `database.json` of the running server are kept: they hold today's licence key and login), and the resources (fetched back to the recorded commits; one that cannot be fetched is reported and left as it is), and starts the server again. **Undo this restore** puts the safety copy back. A backup made by a newer Kora is refused politely; a damaged or cut-off file, a wrong password and a backup of another server are explained.
- **Scheduled backups** (daily or weekly at a time, off by default; the install's last page and the Backups tab suggest turning them on) run from the panel's background service, not from the operating system's scheduler: creating a scheduled task needs administrator rights through a path that is being rewritten, so for now **they only run while the panel's background service runs** (`kora panel --background`); a missed slot is made up once when it starts again. A failed scheduled backup raises an alert in the panel and goes to the server's Discord and generic webhook. The Overview and the servers list show **"No backup yet" / "Last backup 3 days ago"** with a warning when the newest is older than the schedule implies or the last one failed.
- **Move a server to another computer** (Linux or Windows, either way). On the old computer **Move this server** makes a password-protected file; on the new one **Bring a server from a backup or another machine** (a link on the install wizard's first page, and `kora backup import <file>`) takes the file by upload through the panel (streamed to disk, up to 20 GB) or by a path on that computer, asks for the password, shows what the server is, what will be created, what does not come along (the service, firewall rules and port forwarding, the update timer and backup schedule, the GitHub sign-in, the FXServer build) and what is in the way (the name, ports, folder, each with the fix), then builds it in steps that are written down as they finish, so a failure carries on from where it stopped (`start over` removes what was made): a new folder with the settings and txAdmin data converted for this computer (folders in `server.cfg` and txAdmin's files, line endings, ports), the FXServer build, a **new** database and login with the dump loaded and the new login written to `database.json` and `secrets.cfg` (the old login is never reused), the licence key (from the file, or a saved key picked now), the resources at their recorded commits, and the registration. Cfx.re ties a licence key to your account and the server's address: Kora moves the key but cannot make Cfx.re accept it elsewhere, and says so before and after. Afterwards it gives the steps to remove the server from the old computer (it never acts on another machine).
- **Create a support bundle** (Settings, a small link in every error's details, and `kora support bundle [<server>]`): one zip with Kora's version and build, the system, the System check, tool versions, the server list, each server's status, `server.cfg`, `permissions.cfg` and Kora's record (every secret removed), recent jobs and their problems, the activity log, install and update logs, the service, firewall and disk state. Kora shows exactly what is in it and any file's text before anything is saved, saves it on the computer (owner-only) and **never uploads it**. One redaction function (`kora_core::support::redact`) does the removal, deny-by-default: files known to carry secrets (`secrets.cfg`, `database.json`, txAdmin's data, webhook settings, key files, `.env`, the data file) are never read, only listed; everything else is scrubbed for licence keys, webhook addresses, addresses with a login, Git and GitHub tokens, private keys, password hashes, values of settings whose name says secret (cfg, env, YAML, JSON and prose forms), secrets in web addresses and HTTP headers, people's identifiers in permission files and user names in folder paths; a result that still trips the final check is dropped. The GitHub tab's **Report an issue** can add a short cleaned summary of the computer (never the bundle file), and issue titles and text go through the same removal.
- **Backups know about clone / fork and released / latest.** A backup records the server's source (plain copies or your own copies, with the GitHub account), which versions it follows, and for every resource whether it is on its normal version, on a named branch or trying a pull request (its number and title), and the resource page's own `kora-resource-state.json` travels in it. A restore or an import puts each resource back exactly as it was (a resource that was trying a pull request comes back trying it, and shows as not on its normal version) and marks every restored resource as changed, so the "Restart needed" notice is right. Importing on another computer checks whether its GitHub sign-in can use the fork owner and, if not, asks what to do: keep the remotes as recorded, make my own copies here (forks the originals into the account signed in here), or use the originals (the server becomes plain copies). The support bundle lists each resource's branch or pull request and whether a restart is needed.
- **One redaction.** The text of the resource page's diffs and the job history now go through the same function as the support bundle (`kora_core::support::redact`); the older, thinner copies are gone.
- **Deleting a server no longer leaves its backup settings behind**: the settings and the last-backup state are removed (a new server of the same name starts clean) and its backups are kept in a folder of their own and listed under "Backups of servers that no longer exist", from where one can be restored as a new server (`kora backup archived`).
- **Bringing a server in asks for a database administrator login** when the automatic one does not work (the same fields and test as the install wizard; used once, never stored). In the desktop app, "choose a backup file" and "choose a backup folder" open the system dialogs, and a failed backup is a desktop notification that opens the server's Backups tab.
- Operations: `GET /backups`, `GET|POST /servers/{s}/backups`, `PUT /servers/{s}/backups/settings`, `POST /servers/{s}/backups/prune|undo`, `POST /servers/{s}/backups/{id}/verify|preview|restore`, `DELETE|GET /servers/{s}/backups/{id}[/file]`, `POST /backups/import/upload|inspect`, `POST /backups/import`, `POST /support/bundle/preview|file`, `POST /support/bundle`, `GET /support/bundle/{file}`, `POST /support/summary`. New dependencies: `age` (and what it needs: RustCrypto and `i18n-embed`, MIT / Apache-2.0 / BSD) and `regex` (MIT / Apache-2.0).
- Smoke scripts: the Linux install job (Docker MariaDB) backs up, wipes a table, restores and checks the row, makes a password-protected export, deletes the server, imports it as a new one and checks the new database; the Windows MariaDB job does the same.
- **The Kora desktop app (optional): a tray icon and a native window.** `kora-desktop` shows the same panel in a small window (WebView2 on Windows, WebKitGTK on Linux) and puts an icon in the notification area: green when every server runs, amber when something deserves a look, red when something needs attention, grey when the panel is not reachable. Its menu opens Kora, starts, stops and restarts each server, opens txAdmin, checks for updates, pauses notifications and switches "Start with Windows" on and off; Quit says plainly that servers and the background service keep running, and "Quit and turn off Kora's background service" is its own item. Notifications (server stopped, back up, disk/RAM, update ready, and what the page reports while the window is hidden) use the alert rules you already set, are grouped when many come at once, and open the right page when clicked. One copy at a time, close-to-tray with a first-time hint, start with Windows/your desktop (per user, no administrator rights), "Browse..." for the server folder inside the app. A thin client of the panel: nothing changes for the browser route, remote use or a server without a screen, and `kora` itself gained no GUI dependency (the app is a separate program in its own workspace, built by `.github/workflows/desktop.yml`; its decisions are in the tested `kora-shell` crate). See [docs/desktop-app.md](docs/desktop-app.md) (toolkit choice, threat model, the Windows prompt in front of the app, packaging snippets for the MSI and the .deb).
- `kora desktop session` (hidden): the one-line, machine-readable "make sure the panel runs and sign in" that the app uses, with the same logic as a bare `kora`.
- **The Kora shortcut opens the desktop app** when `kora-desktop` is installed next to `kora` (a bare `kora` as before otherwise); `kora app uninstall` also removes the app's start-up entry.
- **HTTPS for the panel.** Any listener other than the loopback address serves HTTPS on the same port once there is a certificate (and says loudly when there is none; `--allow-public` now needs HTTPS or a trusted proxy). Certificates: your own (`kora panel tls set --cert --key`, re-read when the files change, private key file checked), Tailscale's (`kora panel tls tailscale`, fetched and renewed by itself), or a self-signed one from a stable local CA you trust once (`kora panel tls self-signed`, `export-ca`, fingerprints shown). Plain HTTP from other computers is redirected; cookies get `Secure`; HSTS for provided and Tailscale certificates; txAdmin gateway ports, live views and the console use the same TLS. Settings > HTTPS, an HTTPS line in the System check, an expiry warning, `kora panel tls status|set|self-signed|tailscale|auto|off|renew|export-ca`.
- **A reverse proxy you trust, on purpose** (`kora panel proxy trust|forget|status`): forwarded headers are honoured only from the listed address with a shared secret; the visitor's address (not the proxy's) drives the lockout; proxied visitors are always remote. Everywhere else proxied requests are refused as before.
- **Passkeys and one-time codes for remote users.** `kora panel user invite` (or Settings) makes a user and a one-time enrolment link; the person sets up a passkey (WebAuthn) or a password with one-time codes and recovery codes, and signs in with them. Lost device: `kora panel user reset`. "Your sign-in" in Settings lists passkeys, one-time-code status and signed-in devices (with sign out). Sensitive actions from such a session ask for a fresh passkey or code check. API tokens (`kora panel user api-token ...`, Settings) replace tokens for scripts: header only, never in an address. An administrator can require a passkey or one-time codes for everybody. Sign-ins, failures, enrolments, resets and revocations go to the activity log.
- **Saved licence keys in the system keychain**: Linux Secret Service (GNOME Keyring, KWallet) and Windows DPAPI, with the private file as the fallback (servers, no session bus, locked keyring). Settings and `kora keys list` say where each key is kept; `kora keys keychain status|on|off` (and a Settings button) move keys in and out; a key whose entry is gone or unreachable says so and offers to be entered again.
- New operations: `auth_options`, `auth_login`, `auth_enrol`, `auth_reauth`, `auth_account`, `auth_account_change`, `user_credentials`, `user_reset`, `api_tokens_list`, `api_token_create`, `api_token_revoke`, `tls_status`, `tls_renew`, `tls_ca`, `keychain_set`. Migration 5 adds the tables.
- New dependencies: `rustls`, `tokio-rustls`, `rcgen`, `x509-parser`, `webauthn-rs` (+ `webauthn-authenticator-rs` for tests; pure Rust on RustCrypto, no OpenSSL), `argon2`, `hmac`, `sha1`, `qrcode`, `secret-service` (Linux, pure Rust over zbus) and `windows-sys` (Windows, DPAPI). The WebAuthn crates are MPL-2.0 (allowed in `deny.toml` for those crates only).

### Changed
- Progress bars are green, the same colour as the main buttons (they were blue).
- **The panel loads faster.** The UI is split: the first load is 454 kB (146 kB gzipped) instead of 636 kB (191 kB), and the install wizard, Settings, Fleet, System check and each server tab load when first opened. If Kora was updated while a page was open and a part of it is gone, the page now says "This page needs to be reloaded" with a Reload button instead of staying blank.
- **One data file instead of many JSON files.** Kora keeps what it remembers about itself (the server list, saved licence keys, what it remembers about you, stopped installs and saved answers, remote-access settings and users, nodes) in one private SQLite database, `store/kora.db` in the Kora folder (bundled with Kora: nothing to install; see [docs/store.md](docs/store.md)). The panel and a `kora` command running at the same moment can no longer overwrite each other's change: every change is one short transaction. It is as private as `secrets.json` was (`0700`/`0600` on Linux, including the `-wal`/`-shm` files; inherited permissions removed on the folder on Windows), links are refused, and under `sudo` in someone else's Kora folder the files go back to that folder's owner.
- **Upgrading is automatic and keeps everything.** On first start the old files (`servers.json`, `secrets.json`, `profile.json`, `last-install.json`, `panel.json`, `hub.json`, `paused-installs/`) are imported in one transaction and checked, then **moved** (not deleted) to `store/before-sqlite/`. A file that cannot be read is never lost or replaced: the part of Kora that needs it says so and everything else works. A copy of the data file is made before every later change of its format. Going back to 0.7: `kora store export-json` writes the old files (see docs/store.md).
- The server list is stored as JSON per server, so a new field on a server entry needs no database migration; small Kora-folder state files (the reachability consent first) can move into the store as documents without a table of their own.
- Saved licence key values have their own table behind one small trait (`KeyMaterial`), so a later version can keep them in the system keychain.
- `kora uninstall` now asks about deleting your saved keys and remembered names in terms of the data file (answering yes forgets them; the rest of the data file stays).

### Changed
- **No more "Production" and "Development".** A server now has two plain settings: **where the resources come from** (plain clones, or your own copies on GitHub in your account or an organisation) and **which versions** it follows (released versions, or the latest changes). The wizard asks both (and, for your own copies, personal account or organisation, with the guided sign-in and missing-permission messages), the servers list and Overview say "Plain copies, released versions" or "Own copies, latest changes", and the Resources tab can change the versions later. Existing servers keep working: `prod` reads as clones + released and `dev` as own copies + latest, both spellings are written, and `kora install --mode prod|dev` and the API's `mode` still work next to `--source`, `--versions`, `--fork-owner`. See the table in docs/panel.md for what each old difference became.
- **Every server can use branches, pull requests, the GitHub tab, the Schedule tab and the automatic update.** On a server that follows released versions, putting a resource on a branch or pull request is a deliberate, admin-only choice with a clear warning, updates leave it alone, it is shown everywhere with the "not on its normal version" badge, and **Back to the released version** returns to exactly the pinned commit.
- A clone has only `origin` (the original): its pull requests are listed as the original repository's.

### Added
- **Safer GitHub work:** a resource's diff never shows `secrets.cfg`, `server.cfg`, key or password files and hides values of lines that look like keys, tokens or passwords; the audit log records pushes, comments, reviews, merges and forks with the GitHub account that acted (never the text); the title of a pull request being tried is kept with it (`kora-resource-state.json`) and read by the badge; the scheduled update of a server on released versions is tested end to end.
- **The GitHub work of a resource, on its page:** the open pull requests of the original and of your own copy with checks, review state, age and search; a pull request's details (failing checks, files, conversation); comment, approve, ask for changes and merge (as the GitHub account this computer is signed in as, which every such button says; merge is asked first and never bypasses the repository's rules); try a pull request with how far behind it is, **Get the latest commits** and **Stop trying it**; your local changes line by line, **commit**, **push** (never forced), a **new branch**, open a pull request, recent commits; issues (list, comment, report) and releases (what the server is pinned to, what is newer, the notes); **Make my own copy (fork)** for a resource or the whole server, which keeps its version, branch and changes. `kora pr view|comment|review|merge` and `kora resource changes|log|commit|push|new-branch|issues|issue-comment|releases|fork|versions` do the same.
- **A resource that is not on its normal version is highlighted everywhere** with one badge (words, an icon, one warning colour): the Resources list, its page, the servers list and Overview ("2 resources not on their normal version"), the GitHub tab, bulk dialogs, snapshots (which branch each was on), the update check, `kora status`, `kora branch list`. 
- **A page for every resource** (`/servers/<server>/resources/<resource>`, linked from each name in the Resources list): where its files are (normal version, branch, pull request), **Check for update**, **Update** (this resource only), **Start**, **Stop**, **Restart** on the running server, each with progress and a plain reason plus the fix when it cannot work (server stopped: "Start the server"; live console off: link to the Console tab). `kora resource show <server> <resource>` says the same on the command line.
- **"Restart needed: the running server still has the old version."** After an update, a switch of branch, trying a pull request, going back to the normal version, bringing kept-aside changes back or a rollback, the resource page says so, with a restart button right there. Kora keeps this on the server per resource (`kora-resource-state.json` in the server folder: a change number against a restart number), so it survives reloads, shows for every user and the command line, and goes away only when the resource, or the whole server, has really been restarted. A stopped server has nothing old loaded, so no notice.
- **"Can players reach my server?"** A guided checklist on every server's Overview, on the install wizard's finished page and as `kora reach <server>` (`--json`, `--cfx-list`, `--ip-echo`, `--remember`, `--forward on|off`, `--open-firewall`). One line per layer, each OK / probably OK / problem / not known, in plain words: **running** (the game server answers on its port over TCP and UDP, and not only on this computer's own address), **firewall** (what Kora itself opened is known; what it cannot see is said so), **router** (is there a router in between, is it the kind that cannot forward at all, is the port forwarded) and **internet**. Where Kora can act there is a button (start the server, open the port in the firewall, forward the port); where it cannot, the exact values to enter: the router's "Port forwarding" page (TCP and UDP, outside port, inside port, this computer's address), what to tell a hosting provider, and for **carrier-grade NAT** (a shared provider address, 100.64.0.0/10, also a private "internet" address behind a second router) why forwarding cannot work and what to do instead (ask for a public address, a VPS, Tailscale or ZeroTier).
- **No Kora-hosted service, nothing contacted without your yes.** The only way to look at your server from outside is through services you choose: Cfx.re's public server list, asked about your server's own join code (read from its log; Cfx.re already knows it), which says whether you are listed and at which address (a good sign, shown as "probably OK", never as proof: only a player joining proves the UDP port works), and a plain "what is my address" website (`api.ipify.org`) when the router cannot say. Each has its own switch (off by default); the panel says what will be contacted and what it learns before the first use, remembers the choice, and lists what a check contacted. With neither, the internet line says "not known" and guides the manual test ("ask a friend who is not on your network to type `connect <address>`").
- **Automatic port forwarding (optional, per server, off by default).** UPnP, PCP and NAT-PMP, written for Kora (no new dependency for it), with strict parsing and timeouts: only the server's own game port (TCP and UDP), only to this computer, never txAdmin's port or the panel's. It is kept while the server runs (renewed at half the lease by `kora service-host`, and by the panel for servers without a service) and removed when it stops, when the option is turned off, and when the server is deleted or removed from the list. A refusal is explained in words ("another device already forwards that port", "UPnP is read-only on your router"). Turning it on asks first and names the risk in one sentence. The result and the router's own report of its address show in the checklist.
- **Better connect addresses.** The Overview shows the address for your own network, the public address once known (and none behind carrier-grade NAT), and the Cfx.re join link when the server has one, each with a copy button.
- **txAdmin through the panel.** "Open txAdmin" from another computer (Tailscale, a LAN address, an SSH tunnel) used to guess an address and port that was usually closed. Now the panel opens one more port for that server's txAdmin on the same address the panel is reached at (txAdmin's port + 10000, e.g. 40120 -> 50120; bound only where the panel is), signs you in with your panel session and passes everything on to txAdmin on this computer: pages, redirects, cookies and the live console (WebSocket). txAdmin's own port no longer needs to be open for this (the install wizard's "also open the txAdmin port" option stays, with new wording). On the computer that runs Kora, "Open txAdmin" still goes straight to `localhost`. A path such as `/txadmin/<server>/` on the panel's own port cannot work: txAdmin's web app uses absolute addresses (`/socket.io`, `/auth/...`) and has no prefix setting (checked against txAdmin 8.1.2), so the gateway has an address of its own. **Administrators only**, and counted among the risky actions (a remote sign-in made with a token needs `kora panel remote-actions on`, like console input): txAdmin can run code on the server. txAdmin offers no single sign-on, so it asks for its own sign-in; the panel says which account Kora made at install and where the password is saved. See `docs/panel.md` and `SECURITY.md`.
- API: `POST /servers/{s}/reach`, `GET/PUT /reach/settings`, `PUT /servers/{s}/forwarding`, `POST /servers/{s}/reach/firewall`, `POST /servers/{s}/txadmin/ticket`.
- The smoke scripts fetch txAdmin through the panel's gateway as well (Linux service job; Windows service and start steps).

- **Windows code signing, ready to switch on** (`docs/release-signing.md`): a reusable `sign-windows.yml` workflow signs the Windows exe (and the future MSI) through SignPath from an unsigned artifact, verifies the signatures, and rewrites the `.sha256` files from the signed bytes so self-update, `install.ps1`, the service's pinned copy and the build provenance attestation all see the signed file. It does nothing (with a notice) until the secret and variables exist, so releases keep working unsigned until the SignPath application is approved. Includes the SignPath artifact configuration and pipeline policy (`.signpath/`), a comparison of SignPath Foundation, Azure Artifact Signing and a paid certificate, the owner's steps, the exact `release.yml` snippet and the Linux trust notes (checksums, attestation, the planned `.deb`).
- **CI that goes through the panel's real administrator path on Windows** (`.github/workflows/windows-uac.yml`, `docs/windows-uac-ci.md`): an unelevated panel is asked over its API to update itself from a folder only administrators can write to, so the real `runas` / worker / pipe path runs. On GitHub-hosted runners (an elevated account, UAC normally off) it checks that an unelevated administrator token and a standard account never get an administrator worker; on a self-hosted VM with UAC on it also covers approval by policy, the real prompt answered through UI Automation (Yes, No, nobody, a standard account with an administrator's credentials), the pipe being closed to the same user unelevated, and the worker following its panel. Reusable helpers for test accounts, UAC policy, filtered-token launching and token diagnostics are in `scripts/smoke/lib-accounts.ps1`.
- **The panel's TypeScript API types and its client are generated from the Rust side.** `crates/kora-core/src/api/` now describes every operation once (method, path, parameters, request, response, the events and result of a job, and the error shape with its `Action` union); `web/src/api/generated/` is produced from it (a test and a CI step fail when it is out of date), `client.ts` calls operations by name, and the mock backend is type-checked against the same types. How to add an operation is in `CONTRIBUTING.md`. Nothing on the wire changed except the two fixes below.
- **Browser tests for the panel UI (Playwright).** `web/e2e/` runs every main journey in a real browser against the mock backend (first run, the full install wizard, failing steps and their fixes, the Windows permission prompt, licence keys, System check, every server tab, branches and pull requests, updates, Settings, remote roles, two keyboard-only journeys), failing on any console error and on serious accessibility violations (axe); a small smoke layer drives the real `kora panel` binary on Linux (sign-in link, pages, a fake server folder, its tabs). New workflow `e2e.yml`; see CONTRIBUTING.md.
- **Jobs survive a restart.** Updates, installs and the like are recorded as they run (events kept to the newest 1000, secrets never written), so Settings > **Recent jobs** shows history after the panel restarts. A job that was running when the panel was closed (or the computer restarted) shows as "stopped by a restart" with what to do next; an install that used a saved key can be carried on from the install page. (`GET /jobs`, `Op::JobsList`.)
- **Activity log.** An append-only audit log of every change made from the panel (this computer or another device, with sign-in name, provider and role) and from `kora` commands: when, operation, server, who, result; never a secret or request contents. Administrators see it in Settings > **Activity log**; `kora audit` shows it in a terminal. Kept 365 days. (`GET /audit`, `Op::AuditList`, admins only.)
- `kora store restore <backup>` puts a backup of the data file back (refused while the panel runs, backs up the current file first, checks the backup opens and is a version this Kora understands).
- `kora store status`, `kora store backup [--to FILE]` (a consistent copy of the data file, safe while the panel runs) and `kora store export-json [--to DIR]`.

## [0.7.0] - 2026-11-17

This is 0.7.0, "panel first": the web panel is the only interface, nothing needed to get started asks for administrator rights, and failures say what to do and offer the button to do it.

### Fixed
- **Fixes carry on by themselves.** When "Install it for me", the GitHub sign-in or "Start it for me" works from a failed install step, the wizard retries that step automatically and says so (it used to say "you can try that again now"). The same goes for a failed start of the install, the wizard's database test and anything that has its own "Try again". Fix buttons are only drawn for administrators; others are told who can fix it.
- A stopped install is one banner in the wizard ("Carry on" or "Change my answers first"), and counts once for its saved licence key. The disk-space message no longer talks about `--dir` and environment variables, and a full disk points at the folder first. The finished-install page gives the same txAdmin address, connect note and folder button as the server's Overview. One name ("licence key", "pull request") throughout.

### Changed
- **The web panel is the only interface.** Running `kora` (typed, double-clicked or from a shortcut) makes sure the background panel runs and opens your browser at it, and never asks for administrator rights. With no servers yet the panel opens straight into the install wizard (once per browser tab; "Servers" still shows the empty list with "Add an existing server", and the install page links to it: `/?add=1`). On a computer with no screen (SSH) `kora` prints the sign-in link, a ready-to-paste `ssh -L` command and the Tailscale option instead. If the panel is already running it is just opened; if the port is taken the next free one is used; if no background service is possible it runs in that window. Started with `sudo` (Linux) it runs again as the person who typed `sudo`; from an administrator window or a root shell it opens a running panel (on Windows, when the background panel was set up before, it starts it as your normal user through Explorer) or explains what to do. `kora panel --foreground` run as root says the same.
- **`kora manager` and `kora install` with no options are now the same as `kora`** (`kora install` opens the install page). `kora install` with options is unchanged: the scriptable installer.
- **Per-user shortcuts replace the machine-wide "Kora app".** The install scripts and `kora app install` make shortcuts that open the panel and belong to you alone: Start Menu and Desktop on Windows (no administrator rights, not "Run as administrator"), a launcher in the applications menu on Linux desktops (no terminal window). `KORA_NO_SHORTCUTS=1` / `-NoShortcuts` skips them. The server install no longer adds the app in `%ProgramFiles%` / `/opt/kora`, and its options are gone from the wizard (`--no-app` and `--no-desktop-shortcut` are still accepted and ignored).
- **Breaking: `kora app uninstall` is per-user.** It removes Kora's own shortcuts (Start Menu and Desktop on Windows, the applications-menu launcher and its icon on Linux), with `--dry-run`, and needs no administrator rights for that. The OLD machine-wide app from earlier versions is removed with `kora uninstall --app` (as administrator or with `sudo`); `kora app uninstall` run as administrator removes it too, otherwise it says so. `kora uninstall` removes the per-user shortcuts as well (not under `sudo`: they are the user's, so it says to run `kora app uninstall` without it) and the panel's Uninstall list names them.
- **Breaking: the default folder of `kora install` on Windows is `C:\Kora\<name>`**, the same as in the panel (it used to be `%USERPROFILE%\kora\<name>`). Servers already installed keep their folder.
- **Breaking: API errors carry more.** An error may now have `details` (technical text) and `actions` (what the person can do), and its `code` can be a dotted one (`github.gh_missing`, `install.step_failed`, `keys.not_found`, `remote.actions_off`, ...) where it used to be a general one; failures a person can act on answer 422 (403 for `needs_elevation`, which still carries `command`). Scripts that match on error codes need checking: the list is in `crates/kora-core/src/problem.rs`.
- **The install no longer asks you to close the window or run the installer again** when git was just installed, the GitHub sign-in did not finish or permissions are missing: it says what happened and what to do. `kora install` in a terminal prints the same plain message.
- **Remote installs.** Administrators signed in over Tailscale can now install servers and do the destructive actions with no switch to flip first (their identity is verified by the Tailscale service); the operations that stay on this computer (remote-access settings, users, other panels) are unchanged. Administrators signed in with a user token can now install servers and manage them by default; deleting or unregistering a server and uninstalling Kora (and console commands, updating Kora and changing schedules) stay off for tokens until `kora panel remote-actions on` is run on the machine, and the refusal explains why, shows that command and names the other ways. `InstallStart` and `InstallResume` moved out of the destructive class; viewer and operator roles are unchanged. `kora panel remote-actions` now only affects token sessions.
- **A resource on another branch or a pull request is left alone by updates**, manual and scheduled. The update check and the report say "on branch fix-hud" or "trying pull request #12; not updated" (information, not a problem), nothing is pulled into your branch and it is never reported "up to date" by mistake. Going back to the normal version makes updates work for it again. Each snapshot now records the branch a resource was on, and a rollback goes back to that branch before it puts the old commit back, so it can never reset a branch you switched to since (older snapshots have no branch and behave as before). Production servers are not affected: they stay on their pinned releases.
- `kora uninstall` (all servers) keeps your saved keys and remembered names unless you answer yes to a question about them (default: keep; `--yes` keeps them), and asks before removing Kora's own Git and GitHub CLI copies.

### Added
- **Errors that say what to do, with buttons to do it.** When an install, a GitHub action or something that needs administrator rights fails, the panel says in plain words what happened, keeps the technical part under "Show details", and offers buttons for the fixes (try the step again, change an answer, sign in to GitHub, install the missing tool, the command to run as administrator, ...). Other errors get "Try again" and "Copy details".
- **A failed install step can be tried again, or skipped when that is safe, without starting over.** The install stops at the failed step and waits: "Try this step again" carries on from there with the same answers, "Change my answers" goes back to the summary. Only optional steps can be skipped: opening the firewall, the daily update schedule, and starting the server. A pasted licence key that was not saved is kept in Kora's memory only, never written to disk.
- **Saved licence keys, picked by name.** Keys are kept in one private file in the Kora folder, `secrets.json` (created readable only by you: mode 0600 on Linux, inherited permissions removed on Windows, like the per-server `secrets.cfg`; plain text, not encrypted). The install wizard offers a picker ("Main", "Test server", ...) and "Add a new key"; a pasted key is saved by default (name suggested) with a clear switch to not save it. Settings has a **Licence keys** card to add, rename, replace and delete keys, showing which servers use each. The panel and the API never return a full key, only its name and last four characters, and keys never appear in logs, job events, saved answers or error details. Only admins (and this computer) can add, rename, replace or delete keys; other roles that may install or change a key can only pick from the saved names. `kora keys list|add|replace|rename|remove|use` does the same from a terminal (a key is read from `CFX_LICENSE_KEY` or standard input, never from the command line), `kora install --license-key-name <name>` installs with a saved key and `--save-license-key <name>` saves the one in `CFX_LICENSE_KEY`.
- **Change licence key** on a server's Overview tab (and `kora keys use <server> <name>`): pick a saved key or add a new one; Kora writes it where the server keeps it (`secrets.cfg`) and says plainly whether a restart is needed (offering it when the server is running).
- **Stopped installs survive a panel restart when they use a saved key.** The stopped install is written down without any secret (the key is looked up by name when it carries on) and the install page offers "Carry on". A pasted key that was not saved is gone with the restart, as before. Renaming a key updates the unfinished installs and saved answers that use it; deleting one says what will need another key.
- **Remembered Cfx.re name and GitHub owner.** After first use they are kept in a separate non-secret file (`profile.json` in the Kora folder) and pre-filled on the install page, each editable; Settings shows them and can forget them (`kora profile show|forget`).
- **Kora keeps its own Git (Windows) and GitHub CLI (Windows and Linux).** Development installs no longer need `winget`, an administrator prompt or a "close this window and open a new one": Kora downloads a pinned, checksum-verified copy from the official GitHub releases (MinGit and `gh`) into its own folder (`%LOCALAPPDATA%\Kora\tools`, `~/.kora/tools`), unpacks it safely, moves it into place in one step (an interrupted download leaves nothing broken) and uses it without touching the `PATH`. A Git or GitHub CLI that is already on the computer is used first. Git on Linux stays the system package. `kora tools status` shows which copy is used; `kora tools install` sets them up.
- **System check page** in the panel (and `kora check`): Git, the GitHub CLI, the GitHub sign-in, the database and administrator rights, each with its state in plain words and a fix button where something is wrong: **Install it for me** (with a progress bar and, when the download fails, Try again and a manual link), **Sign in to GitHub** (also when only some permissions are missing), **Start it for me** for a database that is installed but not running (`kora check --start-database`: Linux uses the helper when it is installed, otherwise shows the command; Windows asks for administrator rights through the usual `needs_elevation` answer). The same buttons appear wherever an error carries them (the install wizard, the GitHub tab), and those errors link to the System check. The GitHub status tells "the GitHub CLI is not installed", "not signed in" and "signed in without the permissions Kora needs" apart.
- **Change a resource's branch, or try a pull request, from the panel** (Development servers only, administrators only). The GitHub tab has "Branches and pull requests": see which branch each resource is on, switch one to another branch (from your fork or the original repository), try a pull request by picking it from a list or pasting its number or address, and go back to the normal version with one click. The list of pull requests comes from both the original repository and your fork, each labelled with its title, number, author and where it is from. "Several resources at once" shows which resources have a branch before it switches any of them, and can put every resource back to the normal version. The Resources tab shows each resource's branch next to its name. The same from the terminal: `kora branch list|show|switch|default|all|restore` and `kora pr list|checkout`. After a switch Kora says the running server still has the old version, and offers to restart the resource.
- **Your own changes are never lost by a switch.** If a resource has changes you have not saved, Kora does nothing until you choose: keep them aside (they are listed afterwards, with "Bring my changes back"), throw them away (asked twice, with a warning), or cancel. Commits that belong to no branch are saved on a branch of their own before Kora leaves them. Kora never deletes a branch or a kept-aside set of changes, never pushes, and never forces anything.
- **Quick buttons on every server** (the servers list and the server's Overview): **Open txAdmin** (for someone reaching the panel from another computer it uses the name they used, and says what to do when txAdmin's port is closed or they are on an SSH tunnel), **Open folder** (opens the file manager when you are at the computer that runs Kora, and shows the install path next to it) which becomes **Copy path** when the panel is reached remotely or the computer has no desktop (an SSH tunnel counts), and **Copy connect address** (this computer's network address with the server's game port; the page says plainly that players outside your network need your public address and a forwarded port).
- **Tidy up old shortcuts.** When an earlier Kora left its machine-wide app and administrator shortcuts behind, Settings (and a notice on the servers screen) offers one click to make the new shortcuts first and then remove the old copy. Removing it needs administrator rights, so the panel shows the command to run (`kora uninstall --app --yes`) or uses the helper. `kora app status` shows what is found.

- **Windows: the panel asks Windows for administrator permission itself.** An install from the panel no longer stops at "run this command as administrator": Windows asks once when the install starts (the wizard says so beforehand), and the background service, firewall rule, update task and Kora's own MariaDB are set up while you watch the same install. The update schedule, Kora's self-update, "Tidy up old shortcuts", uninstalling, deleting a server that has a service and the System check's "Start it for me" (database) ask once each. If Windows does not get permission (No, nobody answered, or you are signed in from another device, where Kora only asks when you say so) you can ask again, continue without the administrator parts, or see the command. The install's progress and files stay yours, so a failed administrator step can be retried or, when safe, skipped. Behind the prompt is a short-lived elevated copy of Kora that runs only Kora's fixed list of administrator steps (see SECURITY.md).

### Security
- Pre-release review of the 0.7.0 changes. When Kora runs as root through the helper, inside your own Kora folder, it no longer writes `profile.json`, the stopped-install files or `last-install.json` through a link left there (they use a fresh temporary file renamed into place), and files it hands back to you (`secrets.json` and the others) are changed with `lchown`, so a link swapped in meanwhile cannot make root give another file to your account.
- `git` and `gh` are started by the full path of the copy Kora found, never by name, so a `PATH` with an empty or relative entry can no longer make the operating system pick a program from the resource's own folder (a pull request's files) while Kora runs `git` there.
- On Windows a job address such as `CON` or `NUL` can no longer be used to read a device instead of a stopped-install file; a literal `%` in the program path of the Linux launcher is written `%%`.
- **Windows administrator worker hardened** (review of the elevated worker). Its elevated children get an environment built from nothing (system folders from Windows itself, a system-only `PATH`, your own profile folders even when another administrator typed the password), so a variable you or a program set (`KORA_MARIADB_HOME`, `KORA_SELF_UPDATE_API`, `ProgramFiles`, `TEMP`, ...) can no longer steer them; the worker forgets those variables too. Kora's program file is locked from the prompt until the work is done, and the worker checks the panel by file identity, not by path text (8.3 names and `subst` drives work). An elevated Kora never takes a database client from `PATH`. One administrator session at a time, its steps one by one; a step is stopped when the panel goes away or after 45 minutes. Elevated steps, schedule changes and deletes re-check that the server folder is yours (no links on the way), take servers by name from your list (never a folder path), and keep a record of which Windows account each service, firewall rule, update task and database was made for, so one account cannot change another's. The elevated uninstall no longer deletes folders: the panel deletes them afterwards, as you. The firewall step opens no port below 1024 and no remote-administration or database port. A retried service step uses the service an interrupted attempt made instead of failing.
- **Windows: the daily update task runs without elevation.** It used to run with your full administrator token ("Run with highest privileges") on a folder other programs can change; now it runs as you, and you may start and stop that server's service (nothing more), which is all the update needs. Server services keep only the privileges an ordinary user has (no "impersonate a client"). An elevated Kora on Windows now hardens `git` as root does on Linux (no hooks, fsmonitor or repository-chosen programs). A task made by an earlier version keeps its old setting until the schedule is changed once.
- The pull request dialog says that a pull request is someone else's code that then runs on your server. `SECURITY.md` is corrected where it overstated where Git and the GitHub CLI are looked for, and says what a pull request, a token and a saved key can and cannot do.

### Removed
- **The terminal screens** (the `kora-tui` crate: install wizard and server manager). Everything they did is in the panel or the command line. `kora manager` remains only as another name for `kora`.
- **The Windows `winget` / vendor-installer route for Git and the GitHub CLI** (it needed administrator rights and a restart of every open window); the private copies replace it. On Linux the GitHub CLI is no longer installed from GitHub's apt repository either.
- The machine-wide app from the server install and the wizard (see Changed). Code nothing used any more (the old app's install planner now only exists in the tests that set up an old install), the `BSL-1.0` licence from `deny.toml` (only the removed clipboard crate needed it; `ryu` is `Apache-2.0 OR BSL-1.0`), and the last wording that mentioned the terminal screens.

### Security
- **Root no longer trusts files in a server folder.** That folder belongs to the server's own account (which runs third-party resource code) or to you, so before acting as root or administrator Kora now checks everything it reads there:
  - The automatic-update job (root / SYSTEM) only runs a kora program nobody else can change (Kora's root-owned copy in `/opt/kora`, Windows `%ProgramFiles%\Kora\bin`, or `kora` itself when installed in such a place), never a program named in the server's records. Before, anyone who could write the server folder could make root run a program of their choice. The Windows task definition is written to `%ProgramFiles%\Kora\tasks`.
  - `kora delete` and `kora uninstall` only delete inside the server folder and never follow a symbolic link, only remove this server's own `kora-<name>` system account, only delete the program copy in Kora's program folder, hand a kept folder back only to a plain `uid:gid`, never close the SSH port, and with ufw only remove rules carrying Kora's label.
  - Kora's records, the schedule setting and `secrets.env` are written without following planted symbolic links.
- **The helper is limited to what the panel needs**: installs only into a new or empty folder in your home folder or `/home/kora`, no other catalogue, only newer Kora versions; git run as root no longer reads your git settings or runs hooks (your GitHub sign-in still works). The guide now says plainly that the helper gives your account the same power as passwordless `sudo` for Kora's actions.
- **The panel's session cookie is useless on its own.** Browsers send cookies to every port of a host, so txAdmin or a FiveM resource listening on the game port could see the panel's cookie and use it. Every request must now also carry a per-session secret the page keeps for its own address and port. The cookie is named per port (`kora_session_<port>`).
- The panel refuses requests that came through a proxy or `tailscale serve` (they make every visitor look like the computer itself).
- The panel refuses to listen on a public address or on every interface (`0.0.0.0`, `::`) unless you add `--allow-public`: it is plain HTTP.
- Remote sign-in failures are counted per address (IPv6 per /64), so someone guessing tokens only locks themselves out. Remote sessions are limited to 8 live views each and 64 together; server status is read once for every open page; the fleet list is reused for 5 seconds.
- A remote session can only follow a job its role could have started, and "already running" answers no longer show the job's id. The fleet and other panels' servers (the hub) are local only, as documented. From another computer the alert webhook must be a public internet address.
- **FXServer downloads can no longer write outside their folder through symlinks** in the Linux archive. Resources installed from a repository subfolder refuse symlinks, catalogue paths with a drive letter or `:` are refused and every clone or copy must land inside `resources`, and resource names `.`, `..` and names starting with `-` are refused.
- Windows: Kora's folders in `%ProgramData%` must belong to administrators; a folder someone else created first is refused.
- `kora self-update` no longer carries setuid/setgid bits over, and private files can no longer keep looser permissions from a file left behind by an earlier run.
- `kora delete` takes the server's name and ports from your server list, not from files the server's account can change; a folder that is not in the list gets no system-wide changes. Delete only drops databases Kora created, never another server's or MariaDB's own.
- Root never writes into a server folder through a planted symbolic link, hard link or FIFO (update log and lock, state files, configs, secrets), and an install refuses a symbolic link another account could have planted on the way to the server folder. A re-run install always runs the server as its own `kora-<name>` account.
- Older root auto-update jobs that run a program other accounts can change are repaired automatically the next time Kora runs as root.
- A program on the panel's own computer can no longer sign in through the computer's Tailscale address and be taken for its owner.
- Alert webhook addresses set from another computer are read the way they are sent (a backslash can no longer hide the real host), more internal IPv6 forms are refused, and the address is checked again before every send.
- A cookie planted by another service on the same host no longer locks you out; wrong user tokens on ordinary requests count towards that address's lockout; the session secret in a URL is only accepted on live streams.

- The automatic update runs as the person who installed (a "run only when logged on" task on Windows with no stored password; the installing user's git credentials on Linux) instead of SYSTEM, so private forks can be fetched. `--as-system` keeps the old behaviour. Schedules made by older versions are read back as SYSTEM. Linux timers add up to 10 minutes of random delay and catch up after downtime.
- README rewritten; added CONTRIBUTING, SECURITY, Code of Conduct, issue/PR templates and CODEOWNERS. CI cancels superseded runs.

### Security
Fixes from an internal security audit of 0.2.1 (no high-severity findings):
- Downloads follow at most 5 redirects and every hop must be HTTPS (previously a redirect could drop to plain http). A host such as `localhost.evil.example` no longer passes the local-testing exception. Requests time out after 1 hour.
- The Git/GitHub CLI installer is no longer downloaded to a predictable, user-writable temp folder and then run elevated; it now uses a private folder under `%ProgramData%\Kora\tmp` limited to Administrators and SYSTEM.
- On Windows, system tools (`icacls`, `sc.exe`, `netsh`, `powershell`, `git` and others) are now resolved from `System32` / PATH instead of the folder containing `kora.exe`, so a file planted in Downloads can no longer run with administrator rights. `sudo` is only taken from system folders.
- systemd unit paths are validated: server folders containing spaces or `% " \ $ ;` are refused (a folder such as `/srv/a /etc` could have made `/etc` writable to the service). Windows service paths reject `"`.
- The copy of `kora` that the service runs is re-hashed against the hash in its folder name before it is put in place; a swapped file is deleted and the install stops.
- `--license-key` is moved to the `CFX_LICENSE_KEY` environment variable for the elevated copy and removed from the relaunch command line, and Kora warns that a key on the command line is visible in process lists. Prefer the environment variable or the prompt.
- The MariaDB zip extractor now enforces its size limit while copying, not afterwards.
- Known and not fixed: the MariaDB root password is briefly in the arguments of `mariadb-install-db.exe` (administrators only); the MariaDB checksum list is not independent of the download host (now mitigated by the pinned 11.4.13 hash); GitHub Actions are pinned by tag, not commit; `KORA_*` environment overrides are honoured when elevated.

### Fixed
- The Windows MariaDB download no longer crawls or stalls: it shows progress, resumes, and falls back to a second source.
- The automatic update no longer fails on forks of private repositories because it ran as SYSTEM (see Changed).
